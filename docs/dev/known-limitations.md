# 已接受的限制与技术债

记录 Veri Fin **当前已知的架构限制、被有意接受的技术债、以及触发整改的阈值**。与 [tech-decisions.md](tech-decisions.md)（记「已决策」）互补：本文件记「已知会痛、但当前不改或分阶段改」的东西，让隐性认知显性化、可追踪。CI 固定 Flutter 3.47.2；正式包由 CI 构建，须用户明确授权发版，禁止要求清除应用数据。

新发现的限制请登记到此；某项整改完成后从本文件移除。

---

## 已接受的债（定阈值，暂不改）

> 编号一经使用即固定，不得复用或重排；新增条目按 L8、L9… 顺延。其它文档引用时请写编号 + 一句话，避免编号与内容脱节。

### L1 · 数据库 schema 只升不降
- **现状**：`AppDatabase._onUpgrade` 只有升级路径，无 downgrade。用户装了高版本再装回低版本，打开库会命中 `DatabaseErrorApp` 兜底页（明确提示「数据可能还在，别清数据」）。
- **为何接受**：Android 正常渠道不会降级安装；写双向迁移成本高、收益低。
- **缓解 / 约定**：已有兜底页保护用户数据不被误删。发版说明里应提示「不支持降级安装」。改 schema 必须升 `schemaVersion` 并在 `_migrations` 注册迁移段（迁移矩阵测试覆盖从每个历史版本升级）。

### L2 · 退款条目不进通用时间线 —— 跨账户退款的到账账户无独立可见行
- **现状**：退款（`EntryType.refund`）在原支出的「退款」区管理，**不进**交易列表 / 首页 / 账户流水（净额已体现在支出行、带「已退」标记）。退款进的是**到账账户**的余额。当退款退到**与原支付不同的账户**时，那个账户的余额会 + 一笔，但它的交易列表里没有对应的可见行来解释这笔增加。
- **影响**：同账户退款无感（支出行净额已解释）；仅**跨账户退款**时，到账账户会出现「余额变了却找不到对应交易」的轻微困惑。使用频率低。
- **为何暂不改**：把已到账退款渲染成时间线独立行需处理金额显示（退款 `signedAmount=0`）、专用标签、点击跳回原支出、待到账过滤等，改动面不小；当前 per-expense 退款区已提供完整可见性。
- **触发阈值**：收到「跨账户退款账户对不上账」类反馈，或决定做时间线退款行时。届时：`TransactionTile` 为 refund 分支显示 `+金额` 与「退款」标、打开交易详情对 refund 跳 `refundOf`、各列表放行**已到账**退款、过滤**待到账**退款。

### L3 · 无远程崩溃/遥测上报（有意）
- **现状**：全局错误经 `runZonedGuarded` + `FlutterError.onError` 只写**本地** `AppLogger`，用户可在「软件日志」页导出分享；无 Sentry/Crashlytics/Firebase。
- **为何接受**：符合「数据自主、隐私优先、本地优先」定位，是刻意取舍，不是缺陷。
- **代价 / 缓解**：开发者无法主动发现线上崩溃，只能等用户反馈。可考虑「崩溃后引导用户导出诊断日志」的纯本地方案弥补盲区，但不引入任何联网遥测。

### L4 · 汇率完全离线，不做行情与汇兑损益
- **现状**：只支持 ISO 4217 法定货币；汇率由用户按日手工维护或从导入文件带入，应用不联网下载、不后台刷新。跨币转账保存两端实际金额，但不计算外汇持仓成本、已实现/未实现汇兑损益。
- **影响**：频繁跨境消费的用户需要自行补汇率；资产估值可能使用较旧的最近历史汇率，超过 30 个日历日会提示可能过期。缺率时总资产/走势不展示部分和。
- **为何接受**：这是「本地优先、无自有服务端」的明确产品边界；联网行情会引入第三方依赖、隐私披露、可用性和长期维护成本，汇兑损益则需要远超个人记账首版的持仓批次模型。
- **触发阈值**：只有用户明确要求且能提供可审计的数据源/隐私方案时，才单独设计可选联网汇率；不能把网络请求塞进现有离线汇率入口。

### L5 · 多币种金额仍使用 `double` / SQLite `REAL`
- **现状**：金额在领域边界按各币种 minor unit 归一，汇率保留更高精度，但底层仍沿用 `double` 和 SQLite `REAL`，未全量迁移为整数 minor units 或十进制定点数。
- **影响**：大量运算内部可能出现二进制浮点尾差；当前由币种感知舍入、容差比较和零值归一消除用户可见误差。
- **为何接受**：同一版本同时做多币种语义和全库整数迁移会显著放大迁移/备份风险；现有测试已覆盖 JPY/CNY/KWD 舍入和跨币换算边界。
- **触发阈值**：出现无法由 minor-unit 边界归一解决的真实对账问题，或需要高精度会计/证券能力时，另立 schema 迁移设计，禁止局部混用两套存储单位。

### L6 · 部分第三方账单 parser 没有真实 fixture
- **现状**：`test/fixtures/` 只保留钱迹与一木（账单 / 转账 / 退款 / 子分类）的真实导出样例；支付宝、微信、薄荷、Tally 与 CSV 模板的测试用**内联构造的字节**。解析分支有覆盖，但字节不是真实导出。
- **影响**：这些平台的格式变更（列名、编码、金额符号、时间格式）不会被测试自动发现，只能等用户反馈。
- **为何接受**：真实导出含用户隐私，用户已明确表示无法再提供样例，以现有样例为准。**禁止凭空编造第三方格式来"补全" fixture**（AGENTS.md 的「数据、备份与导入」）。
- **触发阈值**：收到某平台导入失败反馈时，先用该平台真实文件补 fixture 再改 parser。

### L7 · 单位显示闸门只看已落库数据，未保存的中间态不参与
- **现状**：是否隐藏单位由 `activeBookUsesMultipleCurrencies` 决定，它只扫**已落库**的四类数据（账户、交易、周期规则、汇率）。编辑页草稿里临时选的币种、导入预览里尚未落库的外币交易、尚未保存的汇率都不参与判定。
- **影响**：单币种账本 + 开启「单币种隐藏单位」时，在记账页把「交易币种」临时切成外币（闸门仍是关的），同一屏的换算行靠 `CurrencyAmountField.forceUnit`（默认 `true`）保住单位，但**大金额走的是偏好闸门**，这一瞬显示成不带单位的 `100`。离开这一屏即恢复：草稿一旦保存，交易落库，闸门随之打开。（转账的手续费不受影响——转账的币种项禁用，币种恒随转出账户。）
- **为何接受**：闸门是在 `_syncAmountFormatContext` 里一次性同步的全局量，改成读控件局部状态会把「哪里显示单位」变成每页各自判断。实际影响只有草稿里的一个数字，且同屏的「交易币种」项已写明币种，不产生歧义。
- **触发阈值**：若出现「同一屏里第二次需要靠单位消歧、而旁边没有币种文字」的位置（例如编辑页将来加「预计余额」或跨币种小计），就把草稿币种并入判定，或给该处显式传 `forceUnit: true`。

### L8 · 少数历史/旧系统路径仍按整份字节处理备份
- **现状**：新版备份与恢复（zip、`.verifin` 加密容器、旧版明文 JSON）全部流式，内存与备份体积无关。仍有两处例外：①**旧版 JSON 加密信封**（密文以 base64 内嵌在 JSON 文本里）解密时要把整份信封读进内存；②**Android 10 以下**把导出文件写入「下载目录」时没有 MediaStore 流式通道，只能整份读出后走系统「保存到」选择器。
- **影响**：只有「旧版本导出的加密备份」或「Android 9 及以下设备导出超大备份」会重新遇到内存上限；新版明文/加密备份与恢复不受影响。
- **为何接受**：旧信封是已冻结的历史格式，为它再做一套流式解密收益有限；Android 10 以下占比极低，且该路径只影响导出、不影响备份与恢复。
- **触发阈值**：收到旧信封解密 OOM 或旧设备导出失败的反馈时，分别补「信封密文流式提取」与「旧系统 SAF 写入通道」。

### L9 · 账单 / CSV 导入仍按整份读入内存
- **现状**：备份与恢复已全链路流式，但第三方账单与 CSV 模板导入仍走 `file_selector`
  （Android 上会把选中文档复制到 `cache/<uuid>/<原名>`）并整份读成字节后解析——包括微信
  xlsx 的 `archive` 解压。读完会删掉插件留下的那份缓存副本。
- **影响**：这些来源是几千行的账单文本，体积通常几十 KB ~ 几 MB，整份读入不构成 Issue 45
  那种内存风险；但确实不是流式的，逐单元格解析大表时峰值随文件增长。
- **为何接受**：账单格式（GBK/UTF-16、xlsx、老式 .xls）解析器都按「完整字节」设计，
  改成流式要么重写各平台 parser，要么先落盘再随机读取，收益与风险不成比例。备份路径才是
  用户数据量会持续增长的地方，已单独流式化。
- **触发阈值**：出现「某个来源的账单文件大到导入闪退」的真实反馈时，先让 parser 支持从
  暂存文件流式/分块读取，再迁移对应平台。

### L10 · 选择器预览 PNG 是随仓库提交的构建产物
- **现状**：Android 12–14 的选择器预览用 `previewLayout` + `previewImage`，内容是 16 张真机渲染的 PNG
  （4 模板 × 浅/深 × 中/英）。它们由 `dart run scripts/widget_previews.dart` 在设备上渲染后拉回仓库，
  **改动组件视觉后必须重跑**，否则选择器里看到的还是旧样式（API 35+ 的生成预览不受影响）。
- **影响**：忘记重导出的版本只在 Android 12–14 的选择器里样式偏旧；桌面上的组件本身、应用内预览与
  API 35+ 生成预览都是新样式，功能与数据无差异。
- **为何接受**：API 31–34 不支持生成预览，静态预览是唯一能显示真机长相的手段；把 16 张 PNG 的导出
  收进一条 Dart 命令（复用仪器测试里的渲染器）已经把维护成本压到一次命令。
- **触发阈值**：出现「选择器预览与真机不一致」的反馈，或不打算再支持 Android 12–14 的选择器预览时，
  要么在发版检查单里固定加一步跑导出脚本，要么删掉 `previewLayout/previewImage` 只留生成预览。

### L11 · 鸣谢名单随版本发布，头像依赖一个已停更的上游
- **现状**：`lib/app/credits.dart` 的鸣谢名单是随包发布的常量，加一位支持者要发一次版；未提供真实头像时，`lib/app/credits_avatar.dart` 用 `Jdenticon.toSvg(称呼)` 生成头像（SHA1 决定图形与色相，再补一层淡彩圆底），算法来自本地 vendor 的 `third_party/jdenticon_dart`。提供 `avatarAsset` 时改为渲染 `assets/credits/` 内的包内图片。
- **为何接受**：名单不联网拉取——应用没有自有服务端，也不该为一张名单开一个网络入口（与「本地优先、无自有服务端」一致）。头像也没有可用的现成库：能按名字生成头像的 pub 包（`multiavatar` / `avatars` / `identicon`）SDK 上限都 <3.0、在当前 Dart 3 上装不上，`boring_avatars` 兼容但采用度极低（2 likes）；`jdenticon_dart` 的算法与 SVG 输出已冻结，但 SDK 上限同样停在 <3.0.0、2021 年后未再发版。因此按「复刻上游到本地」的做法 vendor 一份（只放宽 SDK 约束，MIT 许可与出处见该目录 README）：比自行复刻算法代码量小，图形质量也不必由我们保证。
- **代价 / 缓解**：上游若有修复不会自动进来，需要时 diff 一次 `third_party/jdenticon_dart/lib/`；名单更新滞后一个版本；生成头像会随展示名变化，可用 `seed` 固定，真实头像则直接绑定包内资源。等名单长到需要搜索或分页时再评估展现方式。

### L12 · Controller、交易详情与 MainActivity 仍然过大
- **现状**：`veri_fin_controller_ops.dart` 约 5,273 行，`entry_detail_page.dart` 约 2,380 行，
  `MainActivity.kt` 约 1,514 行。Controller 已按状态/操作拆 part，但操作层仍覆盖交易、账户、
  分类、预算、导入、备份与应用锁；`MainActivity.kt` 同时承载 SAF、更新下载、截图入口与
  小组件桥。
- **影响**：单文件上下文中仍可能出现跨领域修改，代码审查和故障定位成本偏高；当前有
  repository contract、迁移矩阵、控制器原子命令与平台编译门禁兜底。
- **为何暂不一次性重写**：这些文件是运行时咽喉点，整块搬迁会在同一变更中混合行为调整与
  文件移动，难以用现有回归测试证明无行为变化。当前先以“新增领域逻辑不再堆回操作层”为约定。
- **触发阈值**：新增导入/备份或 Android 原生能力再次修改同一大文件超过 200 行，或出现
  两个以上跨领域回归时，按领域拆出导入恢复服务、备份传输服务和 Android `UpdateBridge` /
  `BackupSafBridge`，保持单一 MethodChannel 入口不变。

### L13 · 两个 Android 插件仍应用 Kotlin Gradle Plugin
- **现状**：Flutter 3.47.2 构建 `flutter_timezone`、`home_widget` 时会提示它们仍 apply KGP；当前 debug 构建可以通过。
- **影响**：Flutter 已提示未来版本会拒绝这类插件；升级 Flutter、AGP 或 Kotlin 前必须确认插件已迁移到 Built-in Kotlin，否则 Android 构建会直接失败。
- **为何暂不改**：当前版本可构建，替换/升级插件需要同时验证提醒、时区与桌面小组件行为，不宜在工具链升级中顺手改。
- **触发阈值**：升级 Flutter/AGP/Kotlin，或 CI 出现对应构建失败时，先把这两个插件升级到支持 Built-in Kotlin 的版本，再调整构建配置。

## 有意缓做（评估后判定：高风险 / 低当前收益）

- **偏好类 KV 剥离为独立 notifier**：可修掉「偏好改动触发全树重建」的性能问题，但需把 ~15 个偏好字段搬出 controller、新建独立 scope，**每个读取点都要改**，漏一个即运行时错误；而该性能问题属「规模变大才疼」。判定为中期项，规模/团队变大或出现掉帧后再单独做。**约定：新增偏好一律照主题/语言的独立 `ValueNotifier` 先例做**（`themePreferenceListenable`/`localePreferenceListenable`），不再往全树广播里加。
- **BackupCoordinator 窄接口化**：其静态方法直接接收整个 `VeriFinController`、读六七个成员，是全项目唯一「吃整个 controller」的服务（notification_scheduler、ai_client 都是窄注入）。当前可测（`backup_coordinator_test.dart`）、行为正确，改注入面收益有限，暂不动。触发阈值：新增第二个类似协调器、或备份决策逻辑需要独立轻量单测时，改为窄参数注入（settings、webdavConfig、`exportJson` 回调、logger）。**勿再复制此模式。**
- **`Clock` 依赖注入**：ID 碰撞隐患已通过统一的 `_generateId`（微秒时间戳 + 单调序号）根治；批量/幂等路径（导入计数器、周期规则确定性 id）本就安全。剩余的「时间可控测试」需求已由 `applyDueRecurring(now)` 这类传参覆盖，全量注入 Clock 收益有限，暂缓。
