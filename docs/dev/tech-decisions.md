# 技术决策记录

Veri Fin 关键技术选型与理由。变更相关实现时同步更新本表。源码导航见 [架构导览](architecture.md)。

| 决策 | 选择 | 原因 |
|------|------|------|
| 启动路径与可诊断性 | `main()` 只做绑定初始化与错误捕获，随后立刻 `runApp(VeriFinBootstrap)`；偏好、SQLite、Controller 载入、周期补记、可选的液态玻璃预热在首帧之后由 `StartupCoordinator` 按阶段串行执行。单阶段超过 8 秒置「启动较慢」并允许重试；任一阶段抛错显示阶段、错误与可复制诊断；阶段耗时、首帧与失败原因写入 `startup` 日志。`LiquidGlassWidgets.initialize()` 只在导航样式为液态玻璃时执行、限时 8 秒，超时继续启动。恢复时 `MainActivity` 只在 `savedInstanceState == null` 登记一次性入口 Intent | 旧实现把五段无上限的 `await` 放在 `runApp()` 之前（着色器预热 → KV → 打开 SQLite → 全量载入 Controller → 补记周期账），任何一段慢住都只表现为启动窗口：浅色白屏、深色黑屏，既没有阶段提示也没有恢复入口，刷后台/图标重开只是重跑同一段初始化（Issue 55）。先出帧让启动过程可见，再把可选预热移出关键路径，并让「卡在哪一段」成为用户可复制的诊断事实；限时预热避免第三方着色器编译拖住整个应用 |
| 组件配置引擎日志 | 组件配置引擎（独立 Flutter 引擎）用 `AppLogger.widgetConfiguration` 写 `verifin.logs.widget_config.v1`，主引擎下次启动时合并（按时间 + 级别 + 来源 + 文本去重）并删除该键 | 两个引擎同时整表写 `verifin.logs.v1` 会互相覆盖；独立键既保留配置页的崩溃线索，也不与主引擎的环形缓冲竞争。合并去重保证反复启动不会出现重复行 |
| Android 单平台开发 | 只维护 Android 应用，正式入口在独立 diagnostic flavor 真机运行；电脑上的单元/widget/ffi 测试保留 | 只需维护一套平台能力；缺工具时自动补齐，见 [android-development.md](android-development.md) |
| SQLite 方案 | `sqflite` + `sqflite_common_ffi`（测试） | 单一 API，无需 build_runner 代码生成，符合仓库「不引入额外工具链」约定；drift 需常驻 codegen |
| 分类参照完整性 | 三道防线消除「幽灵同名分类」：① 显示层——`rootIdOf`/`ancestorIds` 遇孤儿/悬空 id 截断不冒名，`categoryByIdFrom` 未知 id 返回「已删除分类」占位（不回退列表首个分类），分类排行下钻按聚合原始 key（`ReportCategoryStat.categoryId`）而非可能被占位的 `category.id`；② 载入/导入时 `_healCategoryData` 自愈——**按记录自己的账本分组**：孤儿/跨账本 parentId 重挂顶级、账本内重复分类（同 label+type+parentId）合并且引用迁移、悬空交易/规则引用与**空分类的收/支交易**归入**该账本**的「未分类」（按键 `uncategorized_<type>` 查找、缺失才以新 id 建一条）、空分类的转账补齐到本账本的「转账」分类，并补齐缺失的系统分类（幂等，收敛循环）；③ DB `categories` 加 `(book_id, label, type, IFNULL(parent_id,''))` 唯一索引（v9→v10 迁移先按同键去重再建索引；v19 迁移把唯一键扩到带上 `book_id`），创建路径（`addCategory`、导入 `resolveCategory`）按 `normalizedCategoryLabel`（trim+小写+全半角）在**同一账本内**查重复用，导入侧 `plan_builder` 对缺失分类兜底到该账本的「未分类」（与自愈同一约定，不产出空 `categoryId`） | 本 App 无同步，重复/悬空分类只可能来自 `importDataJson` 覆盖内部不一致的外部/异构备份（零参照校验）。显示层先保证不冒名；自愈清存量；唯一约束+归一化查重堵源头。唯一索引用表达式 `IFNULL(parent_id,'')` 让顶级分类（parent_id NULL）也参与去重（NULL 在唯一索引中互不相等）；迁移必须「先去重再建索引」否则建索引即失败。自愈必须按账本分组：否则 A 账本的悬空交易会被归到别的账本的分类上，等于跨账本污染 |
| i18n 方案 | Flutter 内置 gen-l10n（ARB，zh 为模板语言） | 官方方案零额外依赖；`generate: true` 由 pub get 自动生成 |
| 语言偏好 | `LocalePreference`（跟随系统/zh/en）存 KV `verifin.locale.v1`，设备本地、不进备份、初始化保留；`MaterialApp.locale` 经 `ValueNotifier` 即时切换 | 语言是设备偏好而非账目数据；null locale 交系统解析、非中文回落英文 |
| 无 context 文案 | 小组件/通知/生物弹窗经 `l10nForPreference(LocalePreference)` 用 `lookupAppLocalizations` 解析，失败回落中文 | 这些场景拿不到 BuildContext；按偏好显式解析保持与应用语言一致 |
| 种子数据语言 | 首启动/初始化按当时语言偏好播种（`systemIsEnglish` 由 main 传入）；播种后属用户数据不再切换 | 账本/分类名是数据不是 UI；随语言反复改名会破坏用户编辑 |
| 备份格式 | 未加密备份为 **zip**（`backup.json` + `attachments/<id>` 图片文件，附件用 store 模式、JSON 用 deflate，附件元数据带 `byteSize`）；新版加密备份为**流式加密容器**（`.verifin`：`VERIFIN-ENC2` 魔数 + 参数行 + AES-GCM 密文 + MAC，密文里是同一个 zip）；导入按 zip 魔数 / 容器魔数自动识别，旧版纯 JSON、旧版 JSON 加密信封仍可导入。**JSON payload 当前为 v4**：分类与标签带 `bookId`（v3 及更早的备份里它们是全局的，导入时展开成每个账本各一份新 id 的副本，并把交易/周期规则/分类预算的引用改写到副本，见 `lib/app/backup/legacy_book_scope.dart`） | 附件以 base64 内嵌 JSON 会让备份随附件急剧膨胀（放大 33% 且每次整份重写），zip 把图片剥离外置；旧信封必须把整份明文读进内存才能加密，GB 级备份会 OOM，故换流式容器；两条写入路径都落缓存文件再流式复制，通道只传路径；魔数识别保证老备份永远可导入。旧备份展开采用**全量复制到每个账本**：旧模型下每个账本看到的本来就是同一张全局表，只有全量复制才能让导入前后的分类集合完全一致，按引用裁剪等于静默删掉用户「建好但还没用」的分类。附件 id 在备份解码和文件入口双重校验，拒绝路径穿越 |
| 跨表命令提交顺序 | 重置、恢复、删账本与账单确认导入先构建完整 `LedgerDataSnapshot`，`await replaceAllLedgerData` 成功后才替换内存与 KV；失败保持旧状态并返回失败，附件物化失败清理本次新文件 | 这些操作跨多张表，逐表 fire-and-forget 或先改内存会造成「界面成功、重启回滚」与跨表悬空引用；忘记密码解锁必须先确认清库事务成功 |
| 备份/恢复内存上界 | 打包用 `ZipEncoder` 增量写盘（附件逐张读、逐张写）、解包用 `ZipDecoder.decodeStream(InputFileStream)` 逐条落盘、加密用 `AesGcm.encryptStream/decryptStream`、平台通道只传缓存文件路径并在原生侧边读边写，旧版明文 JSON 用 `json_events` 前向事件流重写；冷启动只读附件元数据列（`data_url` 逐条读、转换后删列 + VACUUM）；WebDAV 只保留流式上传/下载。单个 ZIP 条目（索引或附件）限制为 64 MiB，并在解压输出端再次限流，防止伪造 header 的 ZIP 炸弹 | 峰值内存只与单张附件、固定分块有关，备份可达 GB 级；原生写盘时同步计算 SHA-256 与字节数，避免整份回读校验 |
| 偏好类数据 | 保留 KV（SharedPreferences），不迁 SQLite | 小而简单，迁移无收益 |
| 数字键盘布局 | `NumberPadLayout.standard/phone` 存 KV `verifin.number_pad_layout.v1`，默认标准布局；设置页随主设置草稿保存 | 数字排列属于设备上的输入肌肉记忆，不影响账目口径，换设备后回到默认布局即可；统一金额数字键盘从 Controller 读取，避免各调用点分叉 |
| SQLite 权威存储 | 账目数据只走 SQLite，不做 KV→SQLite 迁移、不留 KV 回退双路径；`LedgerRepository` 抽为接口，`SqliteLedgerRepository` 为生产实现，全新库首启动播种默认数据 | 只维护一条数据路径，避免双写与回退分支带来的长期隐患；偏好类小数据仍走 KV |
| 测试仓储 | widget/控制器逻辑测试注入 `InMemoryLedgerRepository`（同步、无真实 I/O），数据层真实 SQLite 用 ffi 单独覆盖 | sqflite 的后台 isolate 与 `testWidgets` 的 fake-async 会死锁；内存实现规避且更快 |
| 备份目录 | Android 走 SAF（`ACTION_OPEN_DOCUMENT_TREE` + 持久化 URI 权限 + `DocumentFile`），桌面走 `file_selector` 目录 + `dart:io` | 分区存储下唯一可长期读写用户可见目录的方式；条件导入 `lib/app/backup/backup_storage_*.dart` |
| 备份文件选择 | 恢复入口用自带 `ACTION_OPEN_DOCUMENT` 选择器（`pickBackupFile`）拿 `content://` URI，再交给原生 `stageBackupFile` 流式复制；**不用 `file_selector`**。账单等小文件导入仍用它，读完即删插件留下的缓存副本 | `file_selector_android` 的 `openFile` 会把整份文件读进 Java `byte[]`、经平台通道整份送到 Dart、再复制一份到 `cache/<uuid>/<原名>`；79 MB 备份就同时占三份，GB 级备份会 OOM。它返回普通缓存路径而不是 `content://` URI，不能作为备份恢复入口。自带选择器只有一次流式复制 |
| 备份加密 | `cryptography`（纯 Dart AES-GCM + PBKDF2-SHA256），口令明文存本机 KV | 加密属非简单需求需成熟库；纯 Dart 全平台无原生依赖；口令保护离开设备的备份文件，本机数据本在应用私有区 |
| CSV 导入范围 | 本应用 **CSV 模板**走自研 RFC-4180 解析器，入口用白名单严格校验表头（只允许模板列，`validateCsvTemplateHeader`），**不与第三方软件共用一套表头识别**；支付平台/记账软件账单按来源单独适配（支付宝/微信/薄荷/一木/钱迹/Tally/随手记），各认自己的格式；**各来源 parser 分文件**在 `lib/app/backup/import/`（`Uint8List → ParsedImport` 强类型 `RawImportRecord`，无字符串位置行中间层），账户/分类/标签解析等通用领域逻辑统一在共享 `plan_builder.dart`（`buildImportPlanFromRecords`，唯一一份不按平台复制），`payment_import.dart` 只留枚举 + 注册表 facade（新增平台=写 parser 文件+注册一行）；微信 xlsx 用已有 `archive` 解压 + 正则解析 XML（不引入 `excel`/xlsx 依赖） | 不同软件解析逻辑解耦、各走独立入口才好维护；强类型记录取代字符串位置行，二进制来源（微信序列号/Tally epoch）不再「类型→字符串→类型」往返；微信只导出 xlsx，为体验直接在应用内解析而非要求用户转格式，复用 `archive` 与「手写 XML 正则」惯例避免重量级依赖 |
| 一木记账 .xls 读取 | 一木只导出老式 BIFF8 二进制 Excel（OLE2 复合文档），pub.dev 无库可读（`excel`/`spreadsheet_decoder` 均只支持 xlsx=zip+XML）；自写最小 OLE2+BIFF8 读取器 `xls_reader.dart`（纯 `dart:typed_data`，含 SST 跨 CONTINUE 拆分、RK/MULRK 数字解码） | 应用本地优先、离线可用，不宜要求用户先转格式或引入原生依赖；沿用仓库「手写二进制/XML 解析」惯例（WebDAV、xlsx），只实现账单所需最小记录集 |
| 随手记多工作表 xlsx 导入 | 随手记一个 `.xlsx` 按交易类型导出 10 张工作表（支出/收入/退款/转账/收债/借出/余额变更/负债变更/还债/借入）。`xlsx_reader.dart` 读取全部工作表并按 `workbook.xml` 顺序返回 `XlsxSheet`；`suishouji.dart` 按表名映射、按表头名取列。支出/收入/转账/退款导入，退款因导出没有原支出编号按收入兜底；余额变更正数记收入、负数记支出，落到本账本「余额调整」系统分类（`RawImportRecord.categoryKey` + `plan_builder.resolveSystemCategory` 按键复用/补建）；债务类（收债/借出/还债/借入）与负债变更跳过。账户统一建为现金账户并保留账户币种，余额由导入交易重建；成员/项目/记账人忽略，商家并入备注 | 同一个文件的十张表必须一起读，单表入口会漏掉大部分历史；退款没有原单关联，凭空匹配会改错账，按收入兜底与钱迹孤立退款一致并保证账户余额；余额变更是账户余额的差额，不能当普通收支建用户分类，系统分类才能与 App 内「调整余额」同口径；债务/负债变更无法在不猜账户类型与符号方向的前提下忠实表达 |
| 账单多编码解码 | 引入纯 Dart `charset` 包（支付宝导出为 GBK、薄荷为 UTF-16LE）；读文件按字节、按平台/BOM 解码 | GBK 无成熟纯手写方案（映射表庞大），属非简单需求；`charset` 纯 Dart 全平台无原生依赖，类比加密引入 `cryptography` |
| 平台优先导入 | 用户先选账单来源再选文件（不靠表头猜测），各来源解析后归一到 Veri Fin 规范列再复用 `buildImportPlan` | 同名列/编码/分隔各平台差异大，显式选来源比自动识别稳；归一化让建账户/分类/错误处理只有一套 |
| Tally 导入选 zip 备份而非 CSV 账单 | Tally 同时能导出「备份 zip」（内含 `backup_data.json` 全量 JSON）与「账单 CSV」，选前者：`archive` 解压 + `jsonDecode` 归一 | 其 CSV 账单的时间列只有 `yyyy年MM月dd日`（丢时分），zip 备份的 `date` 是 epoch 毫秒无损；JSON 结构清晰，账户经 assets 数组映射，无需多区块 CSV 解析 |
| 导入预览再落库 | 解析（`controller.parsePlatformImport`，纯解析不落库）与落库（`controller.applyImportEntries`）拆开，中间插入 `ImportPreviewPage`：交易按日期分组（复用 `groupEntriesByDate`/`DateGroupHeader`/`TransactionListCard`）列出，可排除 / 编辑（走 `EntryDetailPage.draft` 草稿模式，返回改后条目而不落库），确认返回 `ImportPreviewResult`，只创建被保留交易实际引用到的新账户/分类/标签。映射区对账户 / 分类 / 标签一视同仁（改名或映射到现有条目）；标签映射到现有标签时把交易 `tagIds` 里的临时 id 改写为现有 id、临时标签不再新建。全程零落库副作用（预览/编辑传「现有＋待新建」的合并账户/分类列表，`accountBalance` 对未落库账户天然返回其初始余额） | 直接入账无法纠错，账单常有脏数据/错分类；预览让用户先核对。`EntryDetailPage.draft` 做成通用「编辑一条交易并返回、不持久化」的模式，后续可复用。以后新增导入平台一律走此流程 |
| 导入的子分类 / 标签 | 归一化规范列在末尾追加 `子分类`、`标签` 两列（其他平台留空、按名解析故向后兼容）；`buildImportPlan` 的 `resolveCategoryHierarchy` 把一级+二级建成「父→子」层级（子分类的去重带 `parentId`，与唯一索引 `(label,type,IFNULL(parent_id,''))` 对齐），`resolveTags` 按半/全角逗号拆分、归一化去重后复用或新建 `Tag`。`applyImportEntries` 只落库被保留交易引用到的标签，并对被引用子分类补建其未存在的祖先候选（父分类不被交易直接引用、否则会被「只建引用到的」过滤丢掉、致子分类悬空） | 一木等来源本就有二级分类与多标签，拍平成顶级分类 / 丢标签会丢失用户结构。追加列而非改位置避免打乱各归一化器按位置对齐的数据行；父级补建保证层级完整，否则只靠 `_healCategoryData` 兜底重挂顶级会丢父子关系 |
| 导入账户/分类映射 | 预览页的可折叠「导入账户 / 导入分类」区：每个待新建账户/分类可**改名**（改 `newAccounts`/`newCategories` 的 name/label）或**映射到现有条目**（`_accountMapTo`/`_categoryMapTo`: 待新建 id → 现有 id）；展示与确认时 `_resolved` 把交易里对待新建 id 的引用整体替换为映射目标，故一次决定对所有引用它的交易生效 | 一份账单常有很多笔属于同一个「新账户」，逐条改账户太繁；按「来源账户名」整体决策一次到位，比逐条多选/逐条询问「是否也替换其它」更省事。映射走 id 替换，落库层 `applyImportEntries` 天然只创建仍被引用的待新建项 |
| 导入缺失分类兜底「未分类」 | 各来源分类名为空的收支记录不落空 `categoryId`：`plan_builder` 的 `resolveCategory` 空名解析到**目标账本**内带「未分类」语义键（`uncategorizedCategoryKey(type)`，与 `_healCategoryData` 自愈同一约定；已有该键的分类则复用，其次复用同名顶级分类，避免撞唯一索引），候选进预览映射区（有该候选时分类映射区默认展开）可整体映射到具体分类；微信 parser 把「交易类型」列（商户消费/微信红包…）映射为分类候选 | 空 `categoryId` 会被展示层回退成「已删除分类」占位、无法筛选与批量处理；语义键让导入与自愈幂等互认、重复导入不再生；「交易类型」虽粗粒度，但配合映射区可一次归到用户自己的分类体系 |

## 账户类型能力矩阵

`AccountType`（`models.dart`）共六种，顺序即选择器展示顺序。两项能力互相独立、各由一个 getter 判定，**新增账户能力相关逻辑一律走这两个 getter，勿硬编码具体类型**：

- `supportsCardLast4`（完整卡号 + 后四位）：仅 **信用卡 / 储蓄卡**。
- `supportsCredit`（信用额度 / 账单日 / 还款日 / 还款）：仅 **信用卡 / 信用账户**。

| 类型 | 枚举值 | 卡号（`cardNumber`/`cardLast4`） | 额度/账单日/还款日/还款（`creditLimit`/`statementDay`/`dueDay`） |
|------|--------|:---:|:---:|
| 网络支付 | `onlinePayment` | ✗ | ✗ |
| 信用账户（花呗/白条） | `creditAccount` | ✗ | ✓ |
| 信用卡 | `creditCard` | ✓ | ✓ |
| 储蓄卡 | `debitCard` | ✓ | ✗ |
| 投资账户 | `investment` | ✗ | ✗ |
| 现金 | `cash` | ✗ | ✗ |

要点：

- **信用账户 vs 信用卡**：花呗/白条有额度和还款但无实体卡号，故 `supportsCredit` 但不 `supportsCardLast4`。储蓄卡有卡号但无额度，反之。信用卡两者皆有。
- **完整卡号与后四位**：`cardNumber`（完整，选填）、`cardLast4`（后四位）、`cardLast4Follows`（跟随开关 bool）三者都**持久化**（落库 + 进备份）。编辑页「后四位跟随卡号」开关（受控组件 `CardNumberFields`，经 `follows`/`onFollowsChanged` 由调用方持久化）打开时后四位自动取完整卡号末四位（`cardLast4Of`），关闭可手填。**开关状态忠实存储、不靠反推**：不能从卡号与后四位反推用户选择，否则会把「用户显式关掉但后四位恰好=末四位」误判成打开。新账户默认 true；缺字段的旧备份/旧账户默认 false（保留其手填后四位、不因跟随空卡号冲成空）。列表/首页只显示后四位，详情页展示完整卡号并可复制。切换到不支持卡号的类型时清空 `cardNumber`/`cardLast4`。
- **额度与本期账单**（纯函数在 `credit_card.dart`）：欠款 = 账户负余额绝对值（`usedCredit`）；可用 = 额度 − 已用（`availableCredit`）。「本期账单」= 当前账单周期（`currentBillingCycle`，上一账单日次日至下一账单日）内本账户支出净额（`billingCycleExpense`），与「当前欠款」是两个互不矛盾的口径（还款是转账不计入本期账单）。**不做**「已出账单未还 vs 未出账单」精确拆分（需跟踪每笔还款销掉哪笔消费的重模型）、分期、年费自动记账。
- **还款**（`CreditRepaymentPage`）：本质是一笔「扣款账户 → 本账户」的转账（`EntryType.transfer`），使欠款减少、不计入收支统计；扣款账户可空串表示「无账户（代还）」。切换到不支持信用的类型时清空 `creditLimit`/`statementDay`/`dueDay`。**转账都带一个「转账」分类**（默认「转出」`transfer_out`），不留空 `categoryId`——App 内记账（`_save` 归一化到 `categoriesForType(transfer).first`）、还款、导入（`plan_builder`）口径一致：空 `categoryId` 会被交易列表按 `categoryByIdFrom` 回退成「已删除分类」占位、也不计入分类管理的转账分类下。载入时 `_healCategoryData` 会把空分类的转账补齐。
