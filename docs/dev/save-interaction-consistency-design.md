# 编辑与保存交互一致性设计与实施记录

> 状态：**已于 2026-08-06 完成实现并通过自动化验收**；Android 预测性返回仍需 release APK 真机复验。
> 关联问题：[GitHub Issue #31](https://github.com/LumiDesk/verifin/issues/31)。
> 第 4 节保留实施前审计快照，第 13 节记录最终落地结果；当前行为以源码、测试和第 13 节为准。

## 1. 背景与目标

本轮改造前，Veri Fin 同时存在三种编辑行为：

1. 页面内修改只保存在本地草稿，必须点击页面上的保存按钮才会落库；
2. 点击选择项、开关或拖动排序后立刻调用 Controller 落库，页面没有统一保存入口；
3. 同一个页面混用以上两种行为——部分字段等待页面保存，另一些子功能却即时落库。

这种差异使用户无法仅凭界面判断“返回会不会丢修改”，也容易形成数据被旧页面快照覆盖的缺陷。Issue #31 就属于第三种：交易详情字段走页面保存，退款却即时落库；随后保存交易详情时，页面用进入时的旧交易快照覆盖了刚刚重算的报销缓存。

本轮目标：

- 建立全应用统一、可预测的编辑/保存/返回语义；
- 有未保存修改时，Header 返回、Android 系统返回和预测性返回走同一拦截逻辑；
- 把真正的编辑操作改为“先改草稿，明确保存后才写 Controller/SQLite/KV”；
- 消除同一编辑页面里“部分草稿、部分即时落库”的混合模式；
- 保存失败时不退出页面、不把失败伪装成成功；
- 不改变筛选、导航、图表交互和明确业务命令的语义；
- 与 Issue #31 一次设计、同一轮实现和验收。

## 2. 术语与边界

### 2.1 编辑会话

用户进入一个页面或弹窗，对一个或一组数据进行修改，最终可以保存或放弃。编辑会话必须有：

- 初始快照；
- 当前草稿；
- 基于“当前草稿是否等于初始快照”的脏状态；
- 唯一明确的最终提交动作；
- 退出时的未保存修改处理。

不能只用“一旦触碰就永久为 dirty”的布尔值；用户把字段改回初始值后应恢复为未修改状态。

### 2.2 明确业务命令

以下操作不是“悄悄自动保存”，而是用户明确要求立即执行的业务命令：

- 删除、清空、初始化、导入、恢复；
- 立即备份、立即上传、下载、检查更新；
- 标记退款已到账、信用账户还款、调整账户余额；
- 启用/停用应用锁等必须即时影响安全状态的流程；
- 新增/重命名弹窗中点击该弹窗自己的“确认/保存”。

这类命令可以在自身确认完成后立即提交，不再要求回到父页面二次保存；破坏性命令仍须使用确认框。此边界已经确认，见第 12 节 D1。

### 2.3 临时界面状态

以下状态不是用户数据编辑，不参与保存与退出拦截：

- 搜索词、筛选条件、报表周期、图表选中点；
- 当前 Tab、临时展开/折叠、选择器内的导航层级；
- 输入法焦点、滚动位置、加载/错误提示；
- 多选模式中尚未执行的选择集合。

如果某个“展开/折叠”当前会持久化为偏好，需要在实现前明确它属于“纯浏览状态”还是“可保存偏好”，不能同名不同义。

## 3. 统一交互规则

### 3.1 全屏编辑页

- 普通全屏编辑页使用 `VeriHeader` 右上角统一保存动作：软碟语义的 `Icons.save_outlined`，tooltip 为“保存”；不再用容易被理解为“完成/确认”的对勾图标表示保存。2026-08 真机长期使用后，快速记账 `EntryDetailPage` 调整为单手高频流程例外：保存语义、Guard 和原子提交均不变，仅把动作移到底部固定主按钮。
- 所有字段只改页面内草稿；保存前不得调用持久化 Controller API。
- 保存成功后默认退出当前编辑页；需要“保存但留在页面”的例外必须在页面清单中注明。
- 草稿未变化时，返回直接退出，不弹窗。
- 草稿有变化时，Header 返回、Android 返回与预测性返回统一弹出未保存修改对话框。
- 新建页是否视为 dirty 由“用户是否实际改变初始草稿”决定；仅打开页面不弹提示。

### 3.2 弹窗和底部 Sheet 编辑器

- 弹窗内编辑先落在弹窗自己的局部状态。
- 必须有明确的“保存/确认”按钮；点击遮罩、下滑关闭或系统返回都不能保存。
- 有修改时尝试关闭，采用与全屏页相同的退出询问。
- 若 Sheet 是父编辑页的一部分，Sheet 的“保存”只更新父页面草稿，不能绕过父页面直接写 Controller。
- 若弹窗本身就是完整、独立的编辑会话（例如重命名标签），弹窗“保存”可以作为最终提交动作。

### 3.3 未保存修改对话框

推荐使用三个动作：

| 动作 | 行为 |
|---|---|
| 保存 | 校验并提交；成功后退出；失败时留在原页 |
| 不保存 | 丢弃本次草稿并退出 |
| 取消 | 关闭对话框，继续编辑 |

- 点击对话框外部或系统返回等价于“取消”，不能隐式丢弃。
- “不保存”属于有损操作，使用警示色但不必采用删除级的强烈红色。
- 保存按钮因校验失败不可执行时，应关闭对话框并把用户带回具体错误字段，不能直接丢弃。
- 异步保存期间禁止重复提交和重复弹窗。

### 3.4 保存成功与失败

- “保存成功”应以对应 SQLite/KV 写入完成为准，而不只是 Controller 内存已变。
- 保存失败时：记录隐私友好的 `AppLogger`、显示用户可见错误、保留草稿和 dirty 状态、停留在当前页面。
- 不允许页面先退出，随后只在上一级页面提示“保存失败”。
- 需要批量修改多个表/多份偏好的保存，应使用单个 Controller 聚合 API；涉及账目多表时必须通过 repository 事务保证原子性。

### 4.3 管理页与直接操作

以下页面主要由一组独立命令构成，不应为了形式一致强行让删除、创建等操作等待整个父页面保存；但拖动排序和裸开关仍需要明确提交边界：

| 页面/区域 | 当前行为 | 推荐目标 |
|---|---|---|
| 分类管理 | 新增/重命名/移动/合并/删除确认后提交；排序拖动即保存 | 保留独立命令；排序进入编辑模式，保存/取消后一次提交 |
| 标签管理 | 新增/重命名/删除确认后提交；排序拖动即保存 | 保留独立命令；排序改为显式保存 |
| 账户分组管理 | 新增/重命名/换图标/删除即时提交；排序拖动即保存 | 弹窗确认视为最终保存；排序改为显式保存 |
| 账本管理 | 新增/重命名/删除确认后提交；点账本立即切换 | 保留；切换账本属于导航/上下文切换，不是编辑 |
| 交易批量操作 | 选择分类/账户后立即批量提交；删除有确认 | 视为明确批量命令；必要时在选择后补最终确认，不引入父页保存 |
| 待退款清单 | “标记已到账”立即提交 | 视为明确业务命令；是否增加二次确认按具体误触风险决定，不纳入父页面保存 |
| 应用锁设置 | 启用/停用/换密码/生物识别验证后立即生效 | 视为安全命令，必须即时生效，不能等待离页保存 |
| 资产页排序 | 拖动后即时保存，排序模式“完成”只是结束 UI | 排序期间只改草稿，“完成”才提交；退出排序询问保存/放弃 |
| 资产背景 | 选中图片/链接后即时保存 | 放入独立外观编辑会话或提供明确保存 |
| 资产分组折叠、视图模式 | 当前即时保存为偏好 | 专门设置/自定义页面中的视图模式改为手动保存；普通浏览折叠不再持久化或移入自定义模式 |

### 4.4 不纳入保存体系

以下页面/交互保持即时的本地 UI 状态，不显示保存：

- 首页、资产/看板报表的浏览与图表交互；
- 交易搜索、筛选、排序、日期范围和多选选择状态；
- 报表维度、周期、下钻状态；
- AI 聊天的流式过程和已经发送的消息；
- 法律文档、日志、Widget 预览等只读页面；
- 系统文件选择器、图片裁剪器在其自身“确认”之前的临时状态。

AI 聊天输入框中尚未发送的文本是否需要离页提示，属于低优先级独立产品问题，本轮默认不纳入。

## 5. 页面返回拦截的统一实现

新增一个共享、轻量的编辑退出机制，避免每个页面复制 `PopScope + Dialog`：

- `EditorExitDecision`：`save` / `discard` / `cancel`；
- `showUnsavedChangesDialog(...)`：统一三按钮对话框；
- `UnsavedChangesGuard`（暂定名）：接收 `isDirty`、异步 `onSave`、可选 `onDiscard`；
- Header 返回继续调用 `Navigator.maybePop`，由 `PopScope` 统一拦截；禁止 Header 和系统返回各写一套逻辑；
- Guard 处理重复返回、保存中状态、成功后放行一次以及 `context.mounted`；
- Android 预测性返回沿用 `PopScope`，不重新引入 `WillPopScope`。

共享件正式落地后须登记到 `docs/dev/components.md`，交互规则同步到 `docs/ui-guidelines.md`。

## 6. Issue #31 与交易聚合编辑

### 6.1 当前根因

`TransactionDetailPage` 首次进入时把交易保存为 `_initialEntry`。添加/编辑退款会立即调用 Controller，Controller 依据关联退款条目重算当前交易的 `refundedAmount`；但页面的 `_initialEntry` 仍是旧值。随后点击页面保存，旧快照通过 `updateEntry` 覆盖当前值。启动时 `_syncRefundData()` 又从退款条目重算，所以重启后恢复正常。

### 6.2 目标模型

交易详情应成为一个完整的“交易聚合编辑会话”，草稿至少包含：

- 原交易可编辑字段；
- 关联退款列表（新增、编辑、删除、待到账/已到账）；
- 图片附件列表（新增、删除）；
- 从退款列表实时派生的 `refundedAmount`、净额和剩余可退金额。

退款 Sheet 的保存和附件选择只修改聚合草稿；只有交易详情页最终保存时才一次性提交。放弃修改时，原交易、退款和附件都不变化。

### 6.3 数据层要求

- `refundedAmount` 继续是 Controller 管理的派生缓存，UI 不得提交任意值；
- `updateEntry` 或新的聚合提交 API 必须在落库前重算退款缓存，防止任何旧调用方破坏不变量；
- 原交易、退款条目和附件应在同一个 SQLite 事务中提交；不能顺序调用三个 fire-and-forget 保存后就退出页面；
- 内存状态应在事务成功后统一更新和通知，失败时保持可解释状态；
- 保存后仍触发现有自动备份与桌面小组件刷新钩子，但只触发一次。

## 7. 草稿与 Controller API 设计

### 7.1 页面草稿

- 简单单模型页面可直接使用模型副本或 Dart record 保存初始值与当前值；
- 多字段、多实体页面定义领域专用 Draft，不引入通用表单框架或新依赖；
- Draft 负责规范化比较，例如文本按最终保存规则 trim 后比较、列表按业务顺序比较；
- UI 预览全部读取 Draft，不通过“先写 Controller 再回滚”实现预览。

### 7.2 聚合提交 API

为页面增加窄而明确的 Controller API，避免页面连续调用多个 setter：

- `saveAccountDraft(...)`；
- `saveBudgetSettingsDraft(...)`；
- `saveAppPreferencesDraft(...)`；
- `savePanelSettingsDraft(...)`；
- `saveTransactionAggregateDraft(...)`。

名称为设计示意，正式实现以现有领域命名为准。API 应：

1. 校验引用与领域不变量；
2. 统一更新内存；
3. 发起必要的 SQLite/KV 写入；
4. 等待写入结果；
5. 成功只通知一次，失败记录日志并把失败返回页面。

不允许为了这次改造把所有 Controller API 泛化成一个配置怪物。

### 7.3 外部变化与冲突

编辑页打开期间，Controller 可能因生命周期、退款命令或其它页面返回而发生变化。实现时：

- Draft 只覆盖自己负责的字段；
- Controller 管理的派生字段与关联数据在提交时重新读取/计算；
- 不得用进入页面时的整个旧模型覆盖当前模型；
- 若目标实体已被删除，保存应失败并提示，不得重新创建幽灵数据；
- 多账本切换时不得把旧账本草稿保存到新账本。

## 8. 保存位置与视觉约定

推荐规则：

- 普通全屏编辑页：Header 右侧使用 `Icons.save_outlined` 保存，并提供“保存”tooltip；
- 快速记账 `EntryDetailPage`：底部使用固定的文字“保存”主按钮，Header 不再重复保存动作；按钮上方不画整宽分割线；
- 固定页脚属于流程本身的页面（导入确认、向导、聊天发送）可保留底部主按钮；
- Sheet/Dialog：底部或 actions 区域使用文字“保存/确认”；
- 排序模式：Header 显示“完成”，完成即提交；退出排序走未保存询问；
- 只读详情页不因为存在独立业务命令就显示保存；
- 保存按钮只在草稿有效且确有修改时可用；草稿未修改时禁用。

## 9. 实施顺序（已完成）

本轮按以下顺序实现与验证：

1. 共享退出对话框、`PopScope` Guard、dirty 比较测试；
2. 已有手动保存页接入 Guard，统一 Header 保存入口；
3. 修复 Issue #31，并把交易、退款、附件改成聚合草稿和原子提交；

## 12. 已确认产品决策

### D1 · 明确业务命令是否豁免页面保存

**决定：豁免。** 删除、导入、立即备份、标记退款已到账、余额调整、还款、应用锁等操作，本身已有明确按钮/确认流程，完成即执行；不再要求父页面二次保存。

若要求所有持久化操作都必须等父页面保存，管理页需要长生命周期的跨实体事务草稿，用户也可能误以为“已还款/已导入”但实际尚未执行，成本和认知负担都会显著增加。

### D2 · 纯偏好类开关是否也全部手动保存

**决定：是，但只限专门的设置/自定义页面。** 主题、语言、触感、小数位、面板开关、提醒时间、资产视图模式等持久化偏好先改草稿，点击页面保存后应用。

资产页普通浏览时的临时折叠建议不再持久化，或移动到专门的自定义/排序模式；否则根 Tab 没有自然的页面保存边界。

### D3 · 未修改时保存按钮状态

**决定：未修改时禁用保存。** 这样能直接表达当前是否有待提交修改；若保存后停留在页面，成功后按钮重新禁用并重置初始快照。

### D4 · 退出对话框按钮数量

**决定：三项——保存 / 不保存 / 取消。** 两按钮“保存/不保存”无法表达“刚才误触返回、我还想继续编辑”，容易造成新的误操作。

### D5 · 交易详情的退款与附件是否随外层统一保存

**决定：统一。** 退款 Sheet 的保存只更新交易详情草稿，附件也只进入草稿；最终由交易详情 Header 保存一次性提交。这样才能彻底消除 Issue #31 所代表的混合保存问题。

如果决定退款 Sheet 的保存本身就是最终提交，则必须明确它是独立编辑会话，并修复旧快照覆盖；但交易详情仍会保留两套提交边界，不符合本轮“同一页面不混用”的核心目标。

### D6 · 全屏编辑页的保存入口是否统一到右上角

**决定：统一到 Header 右上角，并使用软碟保存图标。** 普通全屏编辑页均使用右上角 `Icons.save_outlined`，同时提供“保存”tooltip，不使用对勾表示保存；`EntryDetailPage`、`RecurringRuleEditPage`、`AiSettingsPage` 等现有底部保存按钮随改造迁移。导入确认、分步向导等“继续/执行”型流程保留底部主按钮，Sheet/Dialog 保留自身底部或 actions 区域的保存。

这项只统一编辑页的提交位置，不强行改变只读详情页或明确业务命令的按钮位置。

以上 D1—D6 已于 2026-08-06 经用户确认，并在用户明确授权“开始”后实施。

## 13. 最终实施结果

### 13.1 共享交互

- `SaveHeaderAction` 统一全屏编辑页的软碟保存图标、tooltip 与禁用态；
- `UnsavedChangesGuard`、`EditorExitController` 与 `showUnsavedChangesDialog` 统一 Header 返回、系统返回和预测性返回，提供“保存 / 不保存 / 取消”；
- `SortModeHeaderActions` 统一分类、标签和账户分组管理页的排序入口、取消与显式保存；
- 保存失败返回 `false`，页面保留草稿并停留；删除、初始化等明确命令完成后经 `EditorExitController` 退出，不再被 Guard 误判为普通返回；
- 新建记账和信用账户还款在进入页面时已经携带待创建的业务数据，因此把“尚未创建的实体”本身视为 dirty；普通空白新建表单仍按初始草稿比较。

### 13.2 已改造页面

全屏编辑、设置和排序页面均改为局部草稿后明确保存，包括：记账与交易详情、账户新增/详情、个人资料、主设置、AI 设置、提醒、预算设置、首页概览自定义、面板设置、数据管理偏好、周期规则及启停、还款、导入预览、分类/标签/账户分组排序、资产显示设置。所有全屏保存入口使用 `Icons.save_outlined`。

资产页恢复为浏览页：分区展开/折叠仅是本次浏览状态；视图模式、背景、分区顺序和账户顺序集中到 `AssetDisplaySettingsPage`，一次保存。创建、重命名、删除、导入、备份、还款、余额调整、待退款核销和应用锁等仍按 D1 作为独立明确命令立即执行。

### 13.3 Issue #31 与原子保存

- `TransactionDetailPage` 的交易字段、关联退款和附件组成同一个页面草稿；退款 Sheet 与附件编辑只回写父草稿；
- `VeriFinController.saveEntryAggregateDraft` 在提交前校验退款/附件归属，并仅从已到账退款重新派生 `refundedAmount`，忽略 UI 传入的旧缓存；
- `LedgerRepository.saveEntryAggregate` 在同一个 SQLite 事务中替换交易与附件，事务成功后 Controller 才统一更新内存并通知；
- 添加、编辑、删除退款以及附件保存/放弃、旧快照覆盖和 SQLite 重启一致性均有回归测试。

### 13.4 验证边界

自动化覆盖共享 Guard、主要编辑页面、偏好草稿、排序草稿、交易聚合仓储契约和 SQLite 冷启动。最终合并前执行 `dart format .`、`flutter analyze` 与全量 `flutter test`。Android Header 返回、系统返回和预测性返回的动画/手势体验需继续列入 release APK 真机验收；本轮无 schema 变化。
